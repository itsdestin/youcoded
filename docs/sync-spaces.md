# Sync Spaces, SyncHub, backup & GitHub-connect — depth

Cross-device sync = a hidden per-space git repo the app pushes/pulls, plus SyncHub (instant signals) and a daily backup snapshot. Modules: `desktop/src/main/sync-spaces/`, `sync-service.ts`, `sync-hub-socket.ts`, `sync-error-classifier.ts`, `github-{auth,connect}.ts`. The rule (`.claude/rules/sync-spaces.md`) carries the load-bearing invariants; this file carries the why.

## Git transport (`sync-spaces/git-transport.ts`)

- **`GIT_DIR` env, not `--separate-git-dir`.** separate-git-dir writes a `.git` FILE into the worktree, colliding with a developer's own repo in the same folder. Every git call sets `GIT_DIR=<root>/.youcoded/sync.git` + `GIT_WORK_TREE=<root>`. The contract init test pins "nothing outside `.youcoded/`".
- **`info/attributes` = `* -text`, NOT `* text=auto`.** On Windows `text=auto` overrides `core.autocrlf=false` and converts LF→CRLF on checkout, breaking byte fidelity. `* -text` disables all EOL conversion. Byte-exact contract assertions pin this — run `tests/sync-spaces-git-transport.test.ts` on Windows if you touch EOL config.
- **Ignores in `$GIT_DIR/info/exclude`, attributes in `$GIT_DIR/info/attributes`.** Nothing of ours is ever written into the user's tree (no `.gitignore`/`.gitattributes`). info/exclude is rewritten on every launch's init, dropping earlier oversize lines; the first sync after launch re-detects and re-appends them. An exclude line only silences UNTRACKED files — a tracked file that grew past the cap is re-staged by `add -A` and reset again on every sync.
- **Files over `MAX_SYNC_FILE_BYTES` (50 MiB) never leave the device, whatever let them into a commit.** `unstageOversize()` keeps them out of the commit, but it is not enough on its own: another app copy syncing the same folder (the built app plus a dev instance share `~/YouCoded/`) can re-stage a file between its reset and the commit. On 2026-09-07 that committed six 54–107 MB transcripts on Destin's Z13; a push sends every unpublished commit, GitHub refuses blobs over 100 MiB, and the device uploaded nothing for 9 days while 3,300 commits piled up. So `push()` runs `dropOversizeFromOutgoing()` right before each `git push` (and again before the post-recovery-pull retry). It scans only the unpublished range (`rev-list --filter=blob:limit --filter-print-omitted`). If anything is over the cap, it folds every unpublished commit into ONE whose over-cap files keep their last PUBLISHED version (`reset --soft origin/main` + `reset origin/main -- <paths>`), or leaves them out on a first push. If nothing else is left, it sends nothing (`diff --cached --quiet`). A lock held by another writer skips the cycle, and the state it leaves heals next cycle. Every git call runs with `GIT_LITERAL_PATHSPECS=1`, because a file named `:big` was otherwise read as pathspec magic and uploaded (2026-09-16 review). This is safe because only never-pushed commits are rewritten, the published tip stays the parent, the worktree is never touched and the folded commits stay in the reflog. It refuses loudly if `origin/main` is not contained in `main`, because folding would then revert a peer's changes. Pinned by the "never leaves the device" tests in `tests/sync-spaces-git-transport.test.ts`.
- **Over-cap files are reported, never silently skipped.** `push()` reports files it unstaged this cycle plus files already kept out by an `info/exclude` line that are still over the cap (`excludedOversize`) — a NEW big file is excluded by `pull()` before `push()` looks, so the first half alone never reported it. The engine emits one `oversize` event per file per launch (not every cycle, which flooded the last-50 buffer). The service keeps them in `oversizeBySpace`, and `status().oversize` lists those still over the cap on disk. The Sync box names them via `oversizeNotice()` (`sync-dot-state.ts`) and resolves transcripts to conversation titles.
- **Secrets (`NEVER_SYNC` in guards.ts) are enforced at staging, not just excluded.** `info/exclude` loses to a project's own `.gitignore` (`!.env` re-included a real `.env` into the upload), so `stageAll()` resets any staged secret path — including a `(from …)` copy of one. `reset`, never `rm --cached`: a secret an older version already published stays published but FROZEN (its edits and its local deletion never go out; a propagated deletion would erase it on every other device). No history rewrite.
- **A pull never silently replaces a file git doesn't manage here.** `checkout`/`merge` overwrite ignored untracked files without a word (a fresh device's own `.env` was replaced by the remote's). `holdUnmanaged()` saves every such file the incoming tree touches (plus held-back secret edits, reset first so the merge doesn't refuse) under `$GIT_DIR/youcoded-held/` before the remote lands; `restoreUnmanaged()` runs on every exit: a secret keeps this device's bytes at its own name, anything else becomes a `(from …)` copy.
- **Conflict resolution never guesses on a failed read.** Which sides exist comes from one checked `ls-files -u`; every step is checked; any failure aborts the merge (and removes copies written so far) and throws. A failed probe used to read as "deleted remotely" (a deletion pushed everywhere) or "nothing of ours" (our copy dropped), and a throw mid-loop left conflict markers in the user's file.
- **Convergent conflict policy: REMOTE wins the canonical filename; LOCAL content becomes a visible conflict copy** `name (from <device>, <date>).ext`. Both devices converge to identical trees. Local-wins-canonical never converges (each keeps its own canonical → re-conflict forever). Pinned by the transport contract suite.
- **`merge --allow-unrelated-histories` is load-bearing.** Two devices both with pre-existing content in one space (Personal on a second machine = mainline) have unrelated root commits at first contact; without the flag git refuses the merge and both are silently stuck (`updated:false`/`pushed:false`, no error). Companion: `pull()` adopts remote via `checkout -B main origin/main` when local `main` is unborn.
- **Conflict-copy content read as a Buffer via `showStage()` with `maxBuffer ≥ maxFileBytes`.** The string-returning `git()` helper must never carry file CONTENT: utf8 decode corrupts binary; Node's default 1MB maxBuffer kills `git show` on larger files — which made the conflict loop silently SKIP the local copy while `checkout --theirs` overwrote the file (silent data loss in exactly the scenario the convergent rule protects). Contract tests pin >1MB + binary conflict copies byte-for-byte.
- **`tests/sync-transport-contract.ts` is the transport compatibility boundary (11 tests).** Any new `SyncTransport` (SyncHub-assisted, YouCoded Cloud) must pass it unchanged; changing it = changing spec §15 (do both in one commit). The suite owns its own 120s `vi.setConfig` timeout — don't move that into global vitest config (would mask hung unit tests).
- **`repoNameForSpace` appends a short hash of the LOWERCASED space id.** The repo name IS the sync identity. The slug alone is neither unique ('My App'/'My-App' both slug to `my-app`) nor total (all-symbol/non-Latin → ''). Lowercased-id hashing keeps the name stable across devices while distinct folder names always get distinct repos.

## Corruption & self-repair (`sync-error-classifier.ts`, `sync-spaces/git-transport.ts`, `sync-spaces/repair.ts`, `sync-spaces/engine.ts`)

Full design: `docs/active/specs/2026-07-30-sync-corruption-self-heal-design.md` (workspace path, `youcoded-dev` repo).

**The motivating incident (2026-07-27, Destin's Z13).** Three hard power-loss freezes (a known EC-wedge/s2idle hardware bug) left 16 zero-byte loose objects across three crashes in the Personal space's hidden sync repo. Every subsequent git op on that repo failed — but the transport's old shape turned every failure into a benign-looking result (`push()` returned `{pushed:false}`, identical to "nothing to push"; `pull()` returned `{updated:false}`). Sync was dead for three days while the panel showed green and `lastSync` kept advancing. 3,381 files (three days of conversations) sat staged locally and never reached GitHub.

**The poison mechanic — why a corrupt repo can't heal itself.** A power loss during a loose-object write can land the object's FILENAME (the rename completed) with no CONTENT (the write never flushed) — a zero-byte file. Git checks object existence by filename only, so a plain `git add -A` sees that empty file "exists" and never rewrites it from the intact source file sitting right there in the worktree. The object is *poison*, not just damage: nothing short of deleting the empty file (or nuking the repo) lets git regenerate it. Meanwhile `add -A` keeps succeeding on everything else, so the illusion of health persists until the corrupted ref is actually read.

**The benign-allowlist inversion.** Before this work, `git-transport.ts` treated "no exception thrown" as success and silently mapped most non-zero git exits to a benign-looking result. That default is now inverted: a non-zero exit is **guilty until proven benign**. `assertLocalOk()` (guards local ops — add/diff/commit/checkout/rev-parse) and `throwIfCorrupt()` (guards probe ops whose non-zero exit is often expected, like ahead/behind counts before `origin/main` exists) both run the corruption check FIRST, then fall through to an explicit benign allowlist (`nothing to commit`, lock contention, first-push-no-upstream, offline/empty-remote via `isNetworkFailureStderr`), and throw the real stderr for everything else. Corruption is checked before benign on purpose: a post-crash stderr can carry both an orphaned lock line (not yet aged past `lockStaleMs`) and a corruption line in the same multi-line output, and the benign predicates test the whole stderr while `matchGitCorruption()` (`sync-error-classifier.ts`) is line-based — corruption has to win that race or a real corrupt repo could still read as a stale-lock retry. A corrupt repo now throws a typed `repo-corrupt` error (`REPO_CORRUPT_ERROR_CODE`) that the engine can catch and act on, instead of a `{pushed:false}` a caller has no way to distinguish from "nothing to push."

**Two-tier repair (`sync-spaces/repair.ts`, `GitTransport.repair()`).** `repair()` is an optional transport method (like `maybeGc?`), so non-git transports stay unaffected. It never writes outside `<root>/.youcoded/` — the worktree is read-only to it in both tiers.

- **Tier 1 (surgical, offline-capable).** Reap stale locks, delete every zero-byte loose object (un-poisoning git), verify the local `origin/main` ref resolves and its commit + root tree read (a LIGHT closure check — commit and tree readable — not a full `git fsck`, which times out on real repos, over 2 minutes on the Z13's Personal space), reset `refs/heads/main` to that verified `origin/main`, and delete the index (it may still reference the just-deleted poison hashes; the next `add -A` rebuilds it straight from the worktree, which is the real source of truth). If verification passes, Tier 1 is done — the engine's next sync cycle re-stages everything since the last real push as one snapshot commit and pushes it.
- **Tier 2 (refetch, escalation only).** If Tier 1's verification fails, or the repo is missing/unopenable: move the repo aside as `.broken-<ISO timestamp>` (colons stripped from the timestamp — Windows paths can't contain them), keep only the newest `.broken-*` backup per space (older ones are pruned — corruption recurs on crash-prone hardware, and each backup is a full repo), then re-init fresh. The normal engine cycle re-provisions the remote and pulls, adopting `origin/main`'s real ancestry — so local worktree changes commit as "newer" on top of it, never as an unrelated history that would spawn conflict copies.

Both tiers converge to the same state because the worktree files and the GitHub remote — not the hidden repo — are the two real sources of truth; the hidden `.youcoded/sync.git` is just transport machinery.

**Once-per-launch guard and next-launch escalation.** The engine's `syncSpace` catch calls `transport.repair?.()` on a `repo-corrupt` error, gated by a `healedSpaces` Set keyed per space. The space is marked BEFORE the repair attempt runs (not just on success), so a repair that itself throws or hangs still consumes the launch's one attempt — a second corruption in the same launch means something deeper than ordinary crash damage, and it surfaces as a plain `repo-repair-failed` error instead of thrashing a repair/fail loop at poll cadence. A practical consequence: if Tier 1's light verification misses residual damage that only shows up on the next push, that failure does NOT re-enter `repair()` this run. Escalation to Tier 2 happens on the **next app launch**, when the guard resets and the fresh corruption is seen for the first time — not on the next push within the same session.

**Surfacing.** A successful heal emits a `notice` event (never red): "Sync repaired itself after a crash. Your files were untouched." A failed heal emits an `error` event with `errorCode: 'repo-repair-failed'` carrying the real caught detail — never a guessed cause, per `docs/error-message-standards.md`. No new UI surfaces were added; both ride the existing panel/dot/notice plumbing.

**Launch coverage.** There is no separate boot-time corruption probe. `startEngine` (`service.ts`) already calls `addSpace` then an initial `syncSpace` reconcile for every active space at app startup (`void e.syncSpace(space); // initial reconcile`), so a repo that crashed while the app was closed hits the corruption throw — and heals — in that very first cycle. A dedicated `addSpace`-time probe was considered at plan time and folded away: it would have bought nothing the initial reconcile sync doesn't already guarantee, at the cost of extra machinery.

## Engine & service (`engine.ts`, `service.ts`, `space-manager.ts`)

- **Engine invariants:** single-flight per space + exactly one coalesced rerun (don't add a second queue); `addSpace` waits for chokidar `ready` (with `ignoreInitial:true`, writes before `ready` are swallowed as initial-scan entries — verified on Windows); a persistent `watcher.on('error')` handler is required (post-ready errors bypass `'all'`; an unhandled EventEmitter `'error'` crashes main); `stop()` clears the state map FIRST then awaits in-flight sync chains (their git subprocesses hold handles inside the space root — on Windows that blocks folder removal and races app-quit teardown).
- **Enable/disable serialized through a module-level promise chain in `service.ts`.** `enable(true)` racing `enable(false)` would interleave — disable stops the half-started engine, resuming start adds watchers to a dead instance. `startEngine` is supersession-safe (bails + self-cleans when a newer transition replaced it).
- **Provisioning is REST via the shared `github-client`, not gh (Phase 2, 2026-07-22).** `provisionGithubRemote` delegates to `githubClient.createPrivateRepo` (`POST /user/repos`); an already-existing repo is still SUCCESS (422 → `GET /user` + `GET /repos/{login}/{name}` adopt). The provisioned-URL state file (`~/.claude/toolkit-state/sync-spaces.json`) is per-device, so the second device re-runs provisioning for repos the first created — without the recovery path sync could never start on any device but the first. Token acquisition order (in `github-client.ts`): stored app token (safeStorage, per-install userData — NEVER `~/.claude` or a synced dir) → `gh auth token` → typed "not connected" error. Guards: `github-client.test.ts`, `sync-spaces-space-manager.test.ts`.
- **Git push/pull auth rides a per-invocation inline `credential.helper`, token in child env ONLY (Phase 2).** `credentialedGitInvocation` (git-transport.ts) prepends `-c credential.helper=` (reset) + the inline helper reading `$YOUCODED_GIT_TOKEN` — a helper, NOT `GIT_ASKPASS`, because git consults helpers before askpass, so askpass could never outrank a stale system helper. No token → untouched passthrough (system helper keeps working; no migration). The token never appears in argv or any git config. Auth-refused fetch/push failures throw coded plain-language errors (`classifyGitAuthFailure` — expired vs never-connected by whether a token was used) instead of masquerading as offline/no-op; every other fetch failure keeps the silent offline contract (spec §13). Guards: `sync-spaces-git-transport.test.ts` Phase 2 pins.
- **`errorCode` on error events is the machine contract for auth CTAs.** Thrown errors carry `syncErrorCode: 'github-auth'`; the engine copies it onto the `'error'` event; SyncPanel shows "Connect GitHub…" and `summarizeSpaceSyncError` passes the coded message through verbatim. Match on the code, never the prose. Guards: `sync-spaces-engine.test.ts` (passthrough), `sync-space-error-summary.test.ts`.
- **`isIgnoredPath()` (guards.ts) keeps backups scrub-consistent with sync.** The iCloud backup's cpSync filter interprets the same `DEFAULT_IGNORES` the git layer enforces — a narrower hardcoded filter once leaked `*.pem`/`id_rsa*`/credentials into iCloud while Drive excluded them. New backup targets must route through it (or derive rclone `--exclude` from `DEFAULT_IGNORES`).
- **Friendly GitHub error strings are a UI contract.** "Not connected to GitHub…" / "GitHub sign-in expired…" (github-client) are shown verbatim by SyncPanel's error note (latest `error`-type event in `recentEvents`). Enable-path provisioning failures do NOT reject `enable()` — they arrive as broadcast error events; a new failure path must land in one of those two channels or the user sees nothing.
- **A space with no remote NEVER emits `synced` (2026-07-22 honest-state-machine fix).** `pull`/`push` silently no-op without a remote, and that phantom success superseded the real provisioning error under `latestUnresolvedError` — a fresh device showed green "All synced" having never contacted GitHub (beta.8 VM bug). `engine.syncSpace` now checks `hasRemote` first and calls the injected `ensureProvisioned` hook (service closure: `manager.ensureRemote` + `transport.setRemote`) — so EVERY cycle (poll, debounce, "Sync now") retries provisioning and the failure re-surfaces verbatim each cycle until cured, then heals with no restart. Guard: `sync-spaces-engine.test.ts` honest-state-machine pins.
- **Green is evidence-gated.** `service.broadcast` persists per-space `lastSync` (ms epoch) into `sync-spaces.json` on every real `synced` event (safe to key on the bare type — see previous bullet); `syncSpacesStatus()` exposes it as `spaces[].lastSyncAt`. The panel header derives from the pure `deriveSyncBoxState` (`sync-dot-state.ts`): green requires all active spaces provisioned (`remote` non-null) AND the Personal space synced at least once; provisioned-but-never-synced reads as `hydrating` ("Downloading your synced data…"). Hydration gating is scoped to Personal deliberately — a just-created empty project doesn't sync until its first file change and must not flash the box back to hydrating. Guards: `sync-dot-state.test.ts` (`deriveSyncBoxState`), `sync-spaces-space-manager.test.ts` (persistence).
- **Android has NO real `syncspaces:*` Kotlin handlers (deliberate, pre-Phase-3)** — nine channels share a `{ok:false, error:'not-implemented-on-mobile'}` stub arm in `SessionService.kt` (~:4075) so invokes reject fast. The shared renderer still works: SyncPanel/FolderSwitcher catch + surface inline. When mobile starts, replace the stubs instead of timing out.

## SyncHub — instant signals (Plan 1b; `sync-hub-socket.ts` + worker `SyncGroupRoom` DO)

Metadata-only `{kind, spaceKey}` signals relayed between one account's devices → immediate pulls.

- **DO is per-account (`idFromName(userId)`), never global.** Unlike the social `PresenceRoom` (one global room + D1 friend graph), SyncHub has NO D1 and no cross-account visibility (worker test pins isolation). Auth in the Hono route (`requireAuth`); the DO trusts only internal `X-Sync-User`/`X-Sync-Device` headers — never add a direct DO entry point.
- **The DO is an ACCELERANT, never a source of truth.** Losing its state loses nothing (devices reconcile-on-connect + the engine's 120s poll is the fallback). Don't "optimize" the poll away — SyncHub down must only make sync less instant, never block it.
- **spaceKey across devices = `repoNameForSpace()`, NEVER the local space id.** Local ids (`project:<folderName>`) differ across devices by folder-name case; the repo name (slug + sha1 of lowercased id) is the stable cross-device identity. The service resolves inbound spaceKeys back to spaces by comparing repo names.
- **Signal ONLY on `pushed:true` — the loop breaker.** A signal-triggered pull that pushes nothing broadcasts `pushed:false` and re-signals nothing → converges. Don't widen the guard in `broadcast()` (it also keeps `hub-status`/`error` events from recursing into a send).
- **The hub send in `broadcast()` runs LAST of the fan-outs + isolated (own try/catch); a Personal-pull `runDiscovery()` block follows it.** `broadcast()` is the single fan-out chokepoint from the engine's `onEvent`; a hub failure must never block/kill local window or remote delivery. Signalling is best-effort — the poll covers misses.
- **A superseded `startEngine` run owns NO global state.** The supersession guard (`engine !== e`) sits BEFORE any hub work; everything after is synchronous. Moving hub-socket creation or `hubStatus` writes above it reintroduces the boot-race clobber (a stale run stamps `'off'` over a live socket's `'connected'`) — race-pinned by a service test using the `initialEnabled` boot knob.
- **`hub-status` events carry the sentinel `spaceId: 'hub'`** — never collides with real space ids, so `sync-dot-state.ts`, ProjectHero, per-space scans ignore them naturally. SyncPanel filters them from visible notices (the "Instant sync" line is their surface) but keeps them in `recentEvents`.
- **The relay `kind` allowlist (`ALLOWED_KINDS` in worker `sync/room.ts`) is where Phase 2 lease/takeover kinds get added** — the relay/ring logic is kind-agnostic; extending is a one-line change.
- **`device` is a client-chosen label (`?device=`), connection-pinned — NOT authenticated identity.** Two devices can send the same label; lease logic must never key on it as verified/unique.
- **Per-device sync recency rides the SAME `pushed:true` signal** (migrated 2026-08-12 from the path-scoped rule). The signal now also carries `deviceId` (the machineId) + server `at`; the DO stores a durable per-account `lastSyncByDevice` map (in DO storage) and ships it in `hello`. It is accelerant/presence-grade — losing it degrades a device row to the launch-time `lastSeen` fallback, never breaks. Client exposes it on `getSyncStatus()` + the `status:data` push; renderer's PURE `deviceActivityLabel` (`renderer/components/device-activity-label.ts`, guard `device-activity-label.test.ts`) renders "Synced just now" (<5min) / "Last synced X ago". **Self reads the LOCAL live `lastSyncEpoch`, NOT the map** — the DO never echoes a device's own signal back, so self's own map entry only refreshes on reconnect and would drift stale.
- **Any new DO binding must be mirrored under `[env.test.durable_objects]`** in wrangler.toml (env.test doesn't inherit) or every worker test fails; a new DO class needs a NEW `[[migrations]]` tag (v2 added `SyncGroupRoom`; v1 untouched; migrations NOT repeated in env.test).
- **The hub socket is SERVICE-owned (works with zero windows open)**, unlike the renderer-driven presence socket. Its no-token path retries on a 30s timer via the shared `reconnecting-ws.ts` engine's `noToken: 'poll'` hook (clear-then-reschedule — a fired timeout leaves the var non-null, so an `if (!retryTimer)` guard kills the poll after one cycle; pinned by a socket test) so mid-session sign-in connects without restart. Auth arrives via `setSyncSpacesAuthStore` wired in main.ts BEFORE `startSyncSpaces`.
- **Enable-time pushes send no signal** (socket not open yet) — other devices catch up via poll. By design.

## Import existing folders (`sync-spaces/import-project.ts`)

"Sync this project" + folder-picker import both MOVE the folder into `~/YouCoded/Projects/<name>/`.

- **Import MOVES the folder — never copy-and-keep-both.** The only copy is the EXDEV (cross-drive) fallback, which deletes the source afterward and WARNS if that delete fails. A silent surviving copy forks the user's work (muscle memory edits the old one while the synced copy rots).
- **The EXDEV branch re-checks `existsSync(dest)` BEFORE cpSync — load-bearing.** `rename(2)` reports EXDEV before it looks at dest, so a dest created in the checkImport→move window (the engine materializing a same-named project from another device; dev + built app both running) would be silently MERGED into by cpSync then DELETED by the copy-failure cleanup. The guard refuses instead. Never remove it; never let the failure cleanup run against a dest this call didn't create.
- **The CC transcript slug dir is renamed on move (`remapTranscriptDir`).** `~/.claude/projects/<slug>/` is keyed by a slug DERIVED from cwd (not stored), so past conversations orphan silently unless renamed to the new slug (via `ccProjectSlug`, drive-case-normalized). When the new slug dir exists, merge file-by-file, never clobber.
- **Remap failures degrade to WARNINGS, never errors.** After a successful move, the four store remaps (saved-folders path, central-index path, sidecar manualIncludes/Excludes prefixes, transcript slug dir) are each individually try/caught; a failure means stale pointers, never lost content. Every failure MUST surface a user-facing warning (the sidecar CAS-miss throw exists so even that lands in a warning) — don't reintroduce a silent drop.
- **`remapProjectPath` (central-index) drops any stale entry already at the destination path.** Two index entries sharing one `path` (the store key) shadow each other and detach artifact history; the filter inside the `mutateIndex` lock is the guard.
- **`countFilesBounded` is bounded three ways: file count, depth (100), wall-clock (2s).** `isSymbolicLink()` does NOT detect NTFS junctions — a junction cycle with no files never trips the file-count limit and recurses forever without the depth cap. Depth/time exhaustion returns the OVER-limit signal (fail closed), not a partial count (a partial would let a monster tree into the engine).
- **`FOLDERS_LIST` badges managed rows by projectsRoot PREFIX, not only via the synthesized merge.** The import flow rewrites the saved entry's path to its managed home; prefix-badging keeps the "synced project" label on it.
- **`saved-folders.ts` is the single store module for `~/.claude/youcoded-folders.json`** (`writeFolders` atomic via unique-tmp + rename since dev + built app share `~/.claude`). Known duplication: `remote-server.ts` still hand-rolls the format in its folders:* cases — migrate if you touch those.
- **`ImportProjectModal` close semantics are state-dependent.** Pre-move: Cancel/Scrim/ESC all cancel (ESC gated `!busy`, matching Scrim + Cancel — no dismiss path may bypass the busy guard mid-move). Post-success (warnings shown): EVERY dismiss routes to `onDone(path)` so the folder list reconciles; only pre-move may bare-cancel.

## Project & sync management UX + cross-device discovery

Session picker slimmed to rows + dots + one footer; Project View is the management hub. Discovery/rename/stop: `sync-spaces/{project-registry,materialization-planner}.ts`.

- **Sync dots (green/red/gray) are the ONE sanctioned status-color use.** The tooltip/aria-label carries the full plain phrase; the no-●◐○ rule is about glyph TEXT, not colored dots (Destin chose the dots for the compact picker). All three surfaces (FolderSwitcher, ProjectSwitcher, ProjectHero) derive from the pure `renderer/components/sync-dot-state.ts` — don't re-derive inline; don't change its label strings without the spec (tests byte-pin them).
- **The session picker has NO add/create/import actions** (Project View owns adding, via the "Manage projects…" footer). EXCEPTION: when `onManageProjects` is absent (the buddy window, no Project View), the footer falls back to a minimal "Browse for folder…" escape hatch — delete it if buddy ever gains Project View, don't let it become a second add path.
- **FolderSwitcher's dropdown is PORTALED to document.body at zIndex 9001.** The host SessionStrip menu is the documented z-[9000] exception; a popover spawned FROM it must render above its host, and the menu's `overflow-hidden` clips a non-portaled child. Don't "fix" either z-index.
- **The `data-folder-switcher-portal` marker on the panel is load-bearing (youcoded#113).** A HOST menu's outside-click handler can't see the portaled panel via `ref.contains()`, so SessionStrip checks `target.closest('[data-folder-switcher-portal]')`. Without it a mousedown on the dropdown counts as "outside", the menu unmounts the picker BEFORE its click fires — row selection silently does nothing.
- **Picker rows are pick-only** — rename/remove live in Project View (hero Rename/Remove). Don't re-add per-row actions.
- **`SpaceSyncEvent.at` is stamped ONLY in `service.broadcast()`** (ms epoch at emit) — the SOLE source for "Last synced N min ago". The EVENT stream is still unpersisted (blank after restart until the next sync, by design); distinct from the per-space `lastSync` evidence marker `broadcast` writes into `sync-spaces.json` (2026-07-22), which persists and feeds the green-gating `spaces[].lastSyncAt` — the two answer different questions ("how recently" vs "has it EVER").
- **`syncSpacesSyncNow(spaceId?)` narrows to one space; no-arg syncs everything.** Rides all five parity surfaces (service/ipc-handlers/preload/remote-shim/remote-server). SyncPanel's no-arg call is the compat contract — don't make the arg required.
- **`syncSpacesSyncNow` resolves when the syncs it asked for have FINISHED (2026-09-16), and so does an `engine.syncSpace` call that lands mid-sync.** That call waits for the run in flight AND the one follow-up it queued. The panel's "Syncing…" lasts exactly as long as this promise: the old fire-and-forget version cleared it before git started, so "Try again" looked dead. `deriveSyncBoxState` lets `syncing` outrank a still-unresolved error for the same reason. `startEngine` does NOT await a second Personal sync (it would wait for a whole follow-up run and hold SyncHub/discovery back), and `pushPersonal` does not block rename/stop/description. The remote shim gives this call a 30-minute timeout, because the 30s default would report a slow but working sync as failed. The outcome still arrives as a `synced`/`error` event.
- **ProjectView refreshes sync status live via `syncSpaces.onEvent`** (500ms trailing debounce, gated on view open). Without it "Sync now" produces zero visible feedback.
- **The project registry lives at `~/YouCoded/Personal/ProjectSync/<name>.json` — VISIBLE per-file, NEVER under `.youcoded/`** (that basename is the hidden git dir AND a `DEFAULT_IGNORES` entry → never syncs). `sync-spaces-project-discovery.test.ts` pins round-trip through the transport.

Reuses `laterOf`/`isConflictCopyName`/`extractConflictBase` (`conversations/store-core`) + `mutateFileUnderLock` (`artifacts/cas-write`).
- **Create/import refuse a name that would join another project's online copy** (`projectNameConflict`, service.ts): a name the user stopped syncing (stopped is permanent; the old files would pour into the new folder) or one differing from an existing project only by case (`repoNameForSpace` lowercases — the two would mix files). Refused before anything is created; the modals show the sentence inline.

Copy files left in place (inert). Don't optimize away.
- **Rename is display-name only; the folder never moves** (`repoName` derives from the folder name → no ULID). True on-disk folder rename deferred (spec §15).
- **Stop = tombstone + `engine.removeSpace` + KEEP the folder.** `activeManagedSpaces()` is the ONE gate, routed through all three `roots.spaces()` sites (startEngine add loop, hub-connected sync loop, daily-backup loop) via the service's `activeSpaces()` helper. Don't filter at the sites individually; don't make `ManagedRoots.spaces()` registry-aware.

- **`ensureRemote` runs FIRST in materialize** (uses only `space.id`, so a gh-auth failure creates nothing); `addSpace` runs BEFORE the first pull (a failed pull leaves a recoverable empty space). Materialize reuses the empty-folder + first-sync-pull path — NO `git clone`.
- **`runDiscovery` is single-flight + one coalesced rerun**, reads the registry ON DISK (triggers guarantee freshness). Don't make it sync Personal itself (recurses through the broadcast trigger).
- **Rename/stop ride four-surface IPC parity** via `syncspaces:rename-project`/`stop-project` (`{name,displayName}`/`{name}`); `IPC.SYNC_SPACES_*` in `shared/types.ts` AND the inlined preload map; `ipc-channels.test.ts` pins it. Android stubs `not-implemented-on-mobile`.

## Device registry — "Your devices" (`device-identity.ts`, `sync-spaces/device-registry.ts`)

Per-file convergent records at `Personal/Devices/<machineId>.json` (`{schemaVersion,id,name,platform,lastSeen,updatedAt}`; name LWW by `updatedAt`, `lastSeen` MAX) synced inside the always-present Personal space → the "Your devices" list. Same per-file-under-`Personal/` convention as the Conversation Store and Project Registry, for the same reason (the `.youcoded/` basename is the hidden git dir AND a `DEFAULT_IGNORES` entry — nothing under it ever syncs).

> **M2 note (2026-07-22):** the Conversation Store referenced throughout this doc now splits by provider lane inside the Personal space — `Conversations/claude/<id>.json` + `Conversations/claude/transcripts/<key>/<id>.jsonl` for CC, `Conversations/native/<id>.json` + `Conversations/native/transcripts/<key>/<id>.jsonl` for native sessions. The sync engine/transport treats both lanes identically (they're just files under a managed space root); the lane-assertion guard that refuses a record whose `transcriptRef` points outside its own provider's prefix lives at the conversation-store layer, not here — see `docs/conversations.md` → "Native provider participation".

- **TWO identities live in `device-identity.ts` and must never be merged.** `getDeviceIdentity(userData)` is per-INSTALL and mints a UUID — it is the LEASE id, `userData`-scoped on purpose so the dev instance and built app (which share `~/.claude` but not `userData`) get distinct ids and leases coordinate them cross-process. `getMachineIdentity(builtAppUserData)` is per-MACHINE and is the REGISTRY's — "Your devices" means physical machines, so every profile on one machine must resolve to ONE id. The registry originally reused the per-install id, which made every `YOUCODED_PROFILE` a permanent duplicate row (three "GalaxyBook" rows, 2026-07-16). Don't collapse them in either direction: machine-scoping the lease id makes dev + built app indistinguishable to leases; install-scoping the registry id re-creates the duplicate rows.
- **`getMachineIdentity` is READ-ONLY and returns `null` rather than minting.** It reads the built app's `device-id.json` and never creates one — if a dev profile could mint it, whichever instance launched first would win and orphan the real row. `null` means "no durable machine identity" and the caller MUST register NOTHING. Two cases land there and both want zero rows, not a ghost: the built app has never run on this machine (a dev-only checkout), and `getDeviceIdentity`'s write failed leaving an ephemeral in-memory id. That second case is why durability is structural rather than a nicety — registering an ephemeral id orphans a NEW row on EVERY launch.
- **`main.ts` captures `BUILT_APP_USER_DATA = app.getPath('userData')` BEFORE the dev-profile `setPath` override**, then passes it in — never derive `<appData>/youcoded` inside `device-identity.ts`. Electron derives that folder name from the app name, so hardcoding the current value would silently resolve to `null` — i.e. NO device rows at all, on every platform — the day someone adds a `productName` to package.json. Taking the dir as a parameter keeps the app's folder name out of the identity module entirely.
<!-- verify: {"path": "youcoded/desktop/src/main/main.ts", "contains": "BUILT_APP_USER_DATA"} -->
- **The machine id lives in `%APPDATA%` (Electron `userData`), NEVER `~/.claude`.** `~/.claude` is the directory most likely to be replicated across machines — dotfile repos today, the app's own memory+skills sync roadmap tomorrow — and a replicated machine id silently merges two real machines into one row. `%APPDATA%` is never dotfile-synced.
- **`removeDevice` deletes the canonical `<id>.json` AND every conflict copy that folds into it** — load-bearing, not tidiness. `readDevices` groups by `extractConflictBase` and only checks that the base matches the record's own id; it does NOT require the canonical to exist, so a single surviving `<id> (from X).json` keeps the device listed after a "remove". (The id is a UUID and can never contain `" (from "`, so the Conversation Store's `isConflictCopyName`/`extractConflictBase` apply directly — no `canonicalBaseFor` precedence hack, which the Project Registry needs only because its filenames are user-chosen folder names that may contain parentheses.)
- **Removal is a plain delete, NOT a tombstone** (unlike the Project Registry's `stopped`-dominates state). "Remove" means "forget this device"; a device that is still alive re-registering on its next launch is CORRECT behavior, not a bug. Only a device that never comes back — the case the button exists for — stays gone. Two accepted races, both self-healing and both fixed by pressing Remove again: a rename of this device on ANOTHER machine inside the same sync window survives as a conflict copy created by a LATER merge (after the delete ran) and resurrects the row; and the delete deliberately does NOT take the `mutateFileUnderLock` lock, so a concurrent local write in flight (dev instance + built app) can re-create the file. Don't "fix" either by adding a tombstone — that would make a live device's re-registration impossible.
- **Self-marking uses `machineId` on BOTH IPC surfaces** (`ipc-handlers.ts` + `remote-server.ts` must match exactly — pinned by `ipc-channels.test.ts`). The rows are keyed per-MACHINE, so the per-install `deviceId` matches no row: marking self with it silently marks nothing, and the "cannot remove this device" guard would stop guarding.
<!-- verify: {"path": "youcoded/desktop/src/main/ipc-handlers.ts", "contains": "machineId"} -->
- **`upsertSelf` is heartbeat + create-if-absent; a bare heartbeat never clobbers a synced name.** Absent → create with `name = name ?? os.hostname()`. Present → `lastSeen` always advances, but `name`/`updatedAt` change ONLY when a `name` arg is given and actually differs, so a heartbeat can't overwrite a newer name renamed from another device nor churn `updatedAt` (which is the LWW stamp). `renameDevice` is the mirror: it sets `name` + bumps `updatedAt` but PRESERVES `lastSeen`/`platform`, and refuses an empty name (`parseEntry` rejects empty names on read, so writing one would vanish on the next read). Both skip the write entirely when nothing changed — the callback returning `null` avoids watcher churn + a redundant push.
- **`readDevices` is fail-soft and folds on read.** Corrupt/partial/unknown-schema files are skipped, never thrown — a bad file damages exactly one row, never the whole list (dev + built app share the tree). Conflict copies fold into the canonical in memory (a cross-device rename left as a copy must not lose to the stale canonical); copy files stay on disk, inert. A filename whose base doesn't match the record's own `id` is rejected, keeping a hand-mangled file from folding into the wrong device.

## Legacy backup + demolition (Plan 2c — MERGED to youcoded master, PR #126, 2026-07-15)

Modules: `snapshot-retention.ts`, `conversations/symlink-sweep.ts`, `sync-spaces/gc-policy.ts`.

- **`sweepProjectSymlinks()` is `lstat`-only, removes ONLY symlinks/junctions, NEVER recursive.** Walks `~/.claude/projects/*` one level deep. Removal is `unlinkSync` → `rmdirSync` fallback (Windows dir junctions need rmdir) — NEVER `rm -rf`/`{recursive:true}`, because recursion through a junction deletes the TARGET's real transcripts (the workspace `git worktree remove`-follows-junctions lesson). Per-entry try/catch; idempotent (no once-marker); wired detached in `main.ts`. Don't switch to `statSync` (follows links) or add recursion. **(Highest-consequence: a wrong refactor here irreversibly deletes real conversation transcripts.)**
- **Backups prune only after today's snapshot fully landed on that destination, and never the newest snapshot.** Both paths (spaces `DailyBackup`, legacy `sync-service` + `snapshot-retention.ts`) used to prune after FAILED copies too — weeks of failures (an expired Drive sign-in) would have deleted every snapshot and added none. The day's marker closes only when every destination (spaces: every space too) succeeded; spaces retries only the failed copies (in-memory, per day). Devices share today's dated folder, so copies are newer-wins (`rclone --update`; iCloud keeps timestamps and skips a newer destination file).
- **Drive/iCloud backup is WRITE-ONLY dated snapshots — restore was REMOVED, not rewired.** The `~/.claude` personal set (memory, encyclopedia, settings, skills, config — NOT conversations, which sync-spaces `DailyBackup` covers) writes to `Backup/<YYYY-MM-DD>/`, gated by a once-per-UTC-day stamp, with tiered grandfather-father-son pruning (`snapshot-retention.ts`: ≤7d all → 8–28d newest-per-ISO-week → 29–90d newest-per-month → >90d delete; unparseable folder names NEVER pruned; pruning targets EXACT dated paths via rclone `purge`, never a wildcard). The entire restore path was DELETED (Restore Wizard UI, 9 `sync:restore:*` IPC channels, `restore-service.ts` + adapters). Don't re-add a Restore Wizard or auto-restore-on-launch pull — Drive/iCloud are backup-only; GitHub space sync is the live recovery. (Android Kotlin restore backend left as dead handlers; Phase-3 follow-up demolishes it.)
- **The personal snapshot has an AUTOMATIC daily trigger — an hourly poll, NOT the deleted 15-min loop.** A re-introduced hourly `setInterval` in `SyncService.start()` (+ one launch call) calls `push()` NON-force, so the 15-min `debounceCheck` throttles and the once-per-day stamp gates the dated copy → at most one snapshot/UTC day.
- **The >500MB sync-history warning rides a dedicated `notice` `SpaceSyncEvent` kind, NOT `error`.** `error` drives the red dot; a healthy-but-large space must not flash red. `notice` is emitted after a successful sync (one-per-launch, Set-deduped), IGNORED by `sync-dot-state.ts`, surfaced non-alarmingly in SyncPanel. `git gc` here is **local `git gc --auto` only** (every 50th successful sync per space, counter in the space's `.youcoded/gc-counter`) — repacks local objects, NEVER rewrites history or desyncs peers. Remote/history compaction stays a DEFERRED manual procedure.

## Sync Warnings (`sync-service.ts`, `sync-error-classifier.ts`)

- **`~/.claude/.sync-warnings.json` is authoritative** — a typed `SyncWarning[]` consumed by SyncPanel, StatusBar chips, gear red dot. The legacy string-code `~/.claude/.sync-warnings` is still written by bash `statusline.sh` for the terminal statusline only.
- **Two writers, non-overlapping codes.** `runHealthCheck()` generates `OFFLINE`, `PERSONAL_NOT_CONFIGURED`, `PERSONAL_STALE` (and clears the legacy `SKILLS_UNROUTED`/`PROJECTS_UNSYNCED`, which nothing generates any more). Push methods own per-backend codes (`CONFIG_MISSING`, `AUTH_EXPIRED`, `QUOTA_EXCEEDED`, `NETWORK`, `RCLONE_MISSING`, `UNKNOWN`) + a `backendId`. Health-check merge replaces only its own codes each run — a push-path code must never appear in `runHealthCheck`.
- **`.sync-error-<backendId>` is retired** — deleted on startup by `cleanupStaleBackendErrorFiles()`; all per-backend error state lives in `.sync-warnings.json` keyed by `backendId`. Don't reintroduce.
- **Push-failure warnings are non-dismissible** — `dismissWarning()` enforces `dismissible: false` server-side (silencing "Google Drive isn't connected" risks data loss). No force-dismiss path.
- **Remove a backend → clear its warnings** — `removeBackend()` calls `clearWarningsByBackend(id)`; skipping leaves a phantom warning with no way to dismiss.
- **Classifier stderr patterns are rclone-version-sensitive** (`sync-error-classifier.ts`). Major rclone bumps can silently drop patterns to `UNKNOWN`; `sync-error-classifier.test.ts` is the source of truth for which stderr each code matches.
- **Health warnings must clear themselves — `runHealthCheck()` runs at launch AND every 60s** (`HEALTH_POLL_INTERVAL_MS`, cleared in `stop()` beside the snapshot timer). All three live health codes describe conditions that change *while the app is open*, and the check used to run exactly once, at the end of `start()`. So a launch that lost the DNS race with the WiFi associating wrote `OFFLINE` and left it there: Destin's 2026-08-11 screenshot has a red "No internet" card directly under a green "All synced · 1m ago" header. PR #254 had already fixed the renderer half (a frozen mount-time snapshot) and predicted this remainder in its own last line — after it, every surface read the file faithfully and the *file* was stale.
  Four constraints make the re-run safe, each load-bearing:
  1. **Only the launch run probes for a legacy backend.** The periodic run passes `probeBackends: false`, skipping `autoDetectBackend()`'s `rclone lsd` shell-out — 35s, measured on the Z13 — which must never run at poll cadence. It can't strand a warning: setting up sync mid-session turns on the PRIMARY system, which is a cheap file read.
  2. **`OFFLINE` needs two consecutive failed probes.** One `dns.lookup('github.com')` is a noisy oracle — it fails in the seconds between Electron starting and the WiFi associating, and on any resolver hiccup. That single sample is what produced the bogus card; a recovery resets the counter, so isolated blips never accumulate.
  3. **A dismissed code stays dismissed for the app run** (`wasDismissedThisRun()` in `sync-state.ts`, in-memory by design). Without it the re-check that clears resolved warnings would resurrect dismissed ones a minute later. Non-dismissible codes never enter the set — `dismissWarning()` refuses them first.
  4. **Write only when the set changed** (`sameWarnings()`), or the steady state churns the disk and re-broadcasts identical data every minute. The comparison excludes `createdEpoch`, which is stamped fresh each run and would make every poll look like a change — and skipping the write gives that field the better meaning of "when this condition was FIRST seen".
  Guard: `sync-service.test.ts` (section "runHealthCheck — resolved warnings clear themselves"). Its load-bearing case is "start() keeps re-checking, and stop() ends it" — the sweep-and-rewrite logic was always present, so every other assertion would pass on the old code if you called `runHealthCheck` twice by hand.
- **Node-killed timeouts produce empty stderr — use `extractStderr()`.** `execFileAsync(..., {timeout})` SIGTERMs the child before it flushes stderr, so the rejection has empty `e.stderr` + only `Command failed: <cmd>` in `e.message`. Naively returning `e.stderr || e.message` classifies every timeout as `UNKNOWN` — which broke Drive backups when the youcoded-dev slug grew past 156 MB. `extractStderr(e, timeoutMs)` checks `e.killed && e.signal` and prepends a `TIMEOUT_SENTINEL`. Don't reintroduce raw `e.stderr || e.message` in `rclone()`/`gitExec()`/future helpers.

## Connect-GitHub Modal (`github-auth.ts`, `github-connect.ts`, `github-client.ts`)

In-app GitHub device-flow auth so non-developers never hit the gh-missing/not-signed-in dead end when enabling Sync.

- **The access token NEVER leaves the main process.** It flows ONLY into the github-client store (`setToken` → safeStorage) and `gh auth login --with-token`'s stdin — never logged, never in a thrown Error, never in the `github:connect-done` payload, never over remote WS, never in git argv/config. `github-auth.ts`, `github-connect.ts`, and `github-client.test.ts` all force failures whose messages contain the token and assert it's absent from the surfaced error/payload.
- **The app token store is PRIMARY; gh login is best-effort (Phase 2, 2026-07-22).** The connect flow succeeds when EITHER destination takes the token — a stock machine with no gh completes fully in-app, while a gh-present machine also gets an authed terminal (two-way bootstrap). Login handle comes from REST `GET /user` first, `detectGh` fallback, and is recorded next to the token so `github:status` shows "Connected as X" offline. The modal no longer gates the device flow on gh being installed; the installer stays as an optional extra. Linux without a keychain degrades to a 0600 plaintext file with an explicit log line — NEVER silently (pinned).
- **`github:status` is the COMBINED status** (`combinedGithubStatus`): `authed` = stored app token OR gh login; `installed` stays a gh-CLI fact. SyncPanel's enable-preflight gates on `authed` only. Same payload from ipc-handlers and remote-server.
- **Reuse gh's own public client id (`178c6fc778ccc68e1d6a`) + gh's default scopes** — the minted token is indistinguishable from a normal `gh login`, so the two-way bootstrap and gh's own tooling keep working. Don't stand up a second OAuth app.
- **Do NOT wrap `gh auth login --web` (interactive).** The device flow + `--with-token` is what gh does under the hood, is non-interactive, gives us the code/URL to render, and works while gh is still installing. `completeLogin` MUST `stdin.end()` after writing the token or gh blocks forever on EOF.
- **The orchestrator is a module SINGLETON shared by desktop + remote** (`setGithubConnect`/`getGithubConnect`) so a remote `connect-start` + its `connect-cancel` drive the SAME flow. Its settle guard is PER-FLOW (monotonic `activeFlowId`), NOT a single `settled` bool: two starts without an intervening cancel must let the aborted prior flow no-op while the new one settles — else a superseded flow emits a spurious `cancelled` that blocks the real done. Pinned by the "superseding start silences the aborted prior flow" test.

No PATH-rebuild loop. mac/linux return a `manual` one-liner.

After a successful connect the panel auto re-kicks a failed enable (`wasMidEnableRef`, cleared before re-invoke — one retry, no loop) or, when sync was already enabled, fires an immediate `syncNow` so the header heals without waiting for the poll.

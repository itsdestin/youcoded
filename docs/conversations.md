# Conversation store, leases & Resume Browser identity — depth

Per-conversation JSON records at `~/YouCoded/Personal/Conversations/claude/<id>.json` + CC transcript mirroring, riding the personal sync space; one-holder-per-conversation leases + cross-device takeover; and the Resume Browser's name/path resolution. Modules: `desktop/src/main/conversations/`, `session-browser.ts`, `device-identity.ts`. The rule (`.claude/rules/conversations.md`) carries the load-bearing invariants; this is the why.

## Conversation Store (Phase 2a, `conversations/{transcript-mirror,store-core,conversation-store,reconciler,service}.ts`)

- **Mirror-in is add/update-only AND shrink-guarded** — CC `cleanupPeriodDays` deletion and `/clear` rewrites must NEVER shrink the durable space copy. `transcript-mirror.ts` compares sizes: local missing → no-op (deletion never propagates); local smaller → `{copied:false, shrunk:true}`, space untouched; equal → no write; larger/space-missing → copy. Both directions never delete. The space copy is the durable one. Byte-pinned in `transcript-mirror.test.ts`.
- **`lastActive` comes from the transcript content timestamp, NEVER file mtime.** The reconciler reads `readSessionTranscriptMeta().lastTimestampMs`; a corrupt `>500B` transcript with no parseable tail timestamp is SKIPPED (an EPOCH-dated record would re-upsert every scan forever). The 627-file mtime-rebump incident is why.
- **Merges are convergent (a lattice join), not positional.** `store-core.ts mergeRecords` breaks exact-`lastActive` ties with a total-order content comparison (`JSON.stringify`) so `merge(a,b) === merge(b,a)`. `foldConflictCopies` picks EVERY field group (activity/spread, flags, createdAt, title) over the ORIGINAL input set, not a mutated reduce accumulator — otherwise directory-enumeration order changed the healed record and two devices ping-ponged forever. Literal `'Untitled'` is a placeholder that always loses a real title.
- **The record id/provider is a path-traversal boundary.** `conversation-store.ts` charset-allowlists both (`[A-Za-z0-9._-]`, rejects `.`/`..`, separators, NUL, Windows reserved names) AND `path.resolve`-contains the result under the provider dir. Reachable over the remote WS — don't bypass. Writes throw on a bad id; reads fail soft (null/[]).
- **`sessionProvider` is a REQUIRED param on every store-facing service call (M2, `conversations/service.ts`).** `noteSessionStarted`/`noteTranscriptEvent`/`noteTitleChanged`/`noteFlagChanged`/`noteSessionNote` all take `SessionProvider` explicitly rather than defaulting to `'claude'` — every call site names its lane, so a native caller can never silently write into the CC bucket. `localJsonlPath`/`spaceTranscriptPath` branch on it to pick the CC (`~/.claude/projects/<ccProjectSlug>/`) vs native (`~/.youcoded/sessions/<nativeStoreSlug>/`) source and the `<provider>/transcripts/<key>/<id>.jsonl` space lane.
- **`materializeOne`/`materializeSweep` assert a per-provider LANE PREFIX before touching a transcriptRef, on top of the path-traversal containment check above.** `rec.transcriptRef.startsWith(`${sessionProvider}/`)` is checked FIRST — a record whose provider is `'native'` but whose ref points into `claude/transcripts/...` (or vice versa) is refused with a console warning rather than materialized, so a corrupt/foreign record can never cross-materialize a transcript into the wrong provider's local store. `containedTranscriptPath` (the traversal check) runs after, on the now-lane-verified ref.
- **`lastUsedModel` is a `PortableModelRef` (`{modelId, providerType, providerLabel}`) — deliberately NOT the device-local provider-instance ULID.** `store-core.ts`'s `sanitizeModelRef` whitelist-parses it at all four read/parse sites (record parse, merge, conversation-store read, ipc round-trip) and drops the whole field (never a malformed partial) if any of the three strings is missing — a ULID that only resolves on the device that minted it would round-trip as a broken resume-selector default on every other device. `mergeRecords` rides the newer side's `lastUsedModel` (activity-group field, same as title/device), never a positional/ordering pick.
- **`noteModelUsed` (service.ts) NEVER seeds a record.** It stashes the ref on the session's in-memory ctx and, ONLY if a record already exists for the id, upserts `lastUsedModel` immediately (so the resume selector doesn't wait for the next transcript event); when no record exists yet it is a no-op — an upsert carrying only `lastUsedModel` (no `lastActive`) would recreate the exact §3.2 phantom-record shape (blank transcriptRef, EPOCH `lastActive`, synced everywhere) that `pruneNativePhantomRecords` exists to clean up. The ref rides in on the next real `noteTranscriptEvent` upsert instead (`ctx.pendingModelRef` fold-in).
- **Meta writes buffer until the store leaves `'starting'`, and answer HONESTLY either way (M2, service.ts).** `storePhase: 'starting' | 'ready' | 'unavailable'` gates `metaWrite()`: a call made while `'starting'` queues (`pendingMetaWrites`) instead of racing the store's own boot, and `settlePendingMetaWrites()` drains every queued write in ARRIVAL order once the store resolves to `'ready'` or `'unavailable'` — a write made before the store came up used to silently answer `ok:true` while doing nothing (the 2026-07-19 incident class). `noteTitleChanged`/`noteFlagChanged`/`noteSessionNote` all route through `metaWrite` and return `MetaWriteResult` (`{ok:boolean}`), and every IPC call site (`ipc-handlers.ts`) `await`s the write BEFORE broadcasting `SESSION_META_CHANGED` — broadcast-after-persist, never optimistic.
- **`heal()` claims each conflict copy by quarantine-rename (`<name>.healing-<pid>`) BEFORE reading it.** Without it a multi-process heal (dev + built app share `~/YouCoded`) could unlink a copy the engine just re-created with NEW content at the same day-granular name — deleting it unfolded. Quarantine atomically claims the exact bytes; crash-orphaned quarantines are adopted + folded next heal. Read paths (`get`/`list`) swallow heal failures; `upsert` throws on lock timeout.
- **`upsert` treats caller-provided fields as LOCAL TRUTH.** After `mergeRecords` decides activity fields by recency, provided `projectName`/`originalPath`/`transcriptRef` are re-applied unconditionally and a non-empty/non-`'Untitled'` title is re-applied — the merge is for cross-device convergence, not for overruling the caller. Metadata-only upserts default `lastActive` to the EPOCH sentinel so they never outrank real activity.
- **The materialize sweep and the Resume Browser union both SKIP live sessions (no leases in 2a).** Sweep: `if (sessions.has(rec.id)) continue;` (`service.ts`); union: `if (activeSessionIds?.has(rec.id)) continue;` (`session-browser.ts`). Without these, a pull could `materializeOut` over — or the browser could offer `--resume` against — a transcript CC is actively appending to (Windows EPERM containment unreliable; POSIX rename detaches CC from its inode → frozen chat view + lost turns). Accepted caveat: nothing removes `sessions` entries on session exit, so ended sessions stay sweep-guarded until restart (fine for 2a). `noteSessionEnded` refined in 2b.
- **The reconciler recovers the EXACT projectKey from known folders; last-segment truncation is only a fallback.** The live path keys transcripts by `basename(cwd)` (`youcoded-dev`); the slug last segment truncates hyphenated names to `dev`. A mismatch produces an ORPHAN duplicate space transcript + a cross-device materialize gap. The reconciler builds a `ccProjectSlug(folder) → basename` map (lowercased for Windows case drift) from managed projects + saved folders; truncation applies only to genuinely unknown paths.
- **The LEGACY sync system symlinks every conversation into the HOME-dir slug — the reconciler MUST skip symlinks (youcoded#118).** NOT a Claude Code behavior. `SyncService.aggregateConversations()` symlinks each non-home slug's `.jsonl` into the home slug "for /resume from ~"; `rewriteProjectSlugs()` junctions whole foreign-device slug dirs. Verified in the wild: 687 such 73-byte symlinks, all in the home slug. The reconciler's `statSync` FOLLOWED them → tagged every linked conversation with the home basename (`desti`) and bucketed all transcripts into `transcripts/desti/`. Fix: `lstatSync` + `isSymbolicLink()` skip. Plan 2c (unmerged) additionally deletes the symlink CREATORS and sweeps existing ones; this reconciler symlink-skip is KEPT as a cheap defense against any future symlink source — do NOT remove it.
- **Fire-and-forget store writes MUST `.catch()`** — `upsert`/`setFlag`/`setTitle` reject on lock timeout, and an uncaught rejection in Electron main is fatal-ish. `service.ts` routes every write through a catch; never `void store.x()`.
- **The reconciler preloads all records via ONE `store.list()` pass, not `store.get()` per file.** `get()` heals (readdirs the whole provider dir); per-file gets made the scan O(n²) in dirents (~2.8s at 600 records every startup + 30-min tick). Preload is ~200× fewer reads.
- **The store works with sync OFF.** `startSyncSpaces()` always runs + populates `getManagedRoots()`; only the engine is gated on the enable flag. Records write locally regardless; they don't travel until sync is enabled.
- **Known 2a limits:** a store-only browser row on a second device can transiently read "Not synced to this device yet" until the same-pull sweep materializes the transcript (self-corrects next open); transcripts >50 MB hit `MAX_SYNC_FILE_BYTES` and never reach peers.

## Session leases & takeover (Plan 2b, `conversations/{takeover,lease-client,service}.ts`, `device-identity.ts`)

One-holder-per-conversation coordination + cross-device takeover, on the Conversation Store (2a) + SyncHub (1b). DORMANT behind `native.supported=false`/`YOUCODED_NATIVE` EXCEPT the materialize-on-release, Bug-1 browse filter, and SessionStart-lease-acquire paths, which run for real CC sessions (null-safe when sync/hub absent).

- **Lease ops are DO-AUTHORITATIVE request/response, NOT client-relayed signals.** `{type:"lease", op:acquire|renew|release|takeover|force-acquire|get}` hits the `SyncGroupRoom` DO, which owns the lease table with server-computed lazy 300s expiry (30s heartbeat) — the DO is the single arbiter, unlike the `space-updated` SIGNAL relay that just fans out. Don't route lease decisions through the signal path.
- **`lease-event` broadcasts (released/taken/takeover-request) NEVER enter the replay ring.** A replayed stale lease frame would LIE about current state (assert a holder that already released). Lease state is re-queried live via `op:get`, never reconstructed from replay. `ALLOWED_KINDS` stays `{space-updated}` — leases are a separate message TYPE, so the "lease-acquired is a disallowed signal kind" worker test still holds.
- **Leases key on the per-INSTALL `deviceId` (`getDeviceIdentity(userData)`), NEVER the client-chosen device LABEL.** `device-identity.ts` mints a UUID in Electron `userData/device-id.json`. Per-install (not per-machine) is load-bearing: the dev instance and built app share `~/.claude` but have SEPARATE `userData`, so distinct deviceIds coordinate them cross-process on ONE machine. The SyncHub `device` label is a display string two devices can share — never key a lease on it.
- **Do NOT swap the lease id for `getMachineIdentity()`.** `device-identity.ts` exports TWO ids that must never be merged: the per-INSTALL one above (leases) and a per-MACHINE one (the DEVICE REGISTRY's — "Your devices" means physical machines, so every profile on a machine resolves to one id). They pull in opposite directions by design: machine-scoping the lease id makes the dev instance and built app indistinguishable to leases — exactly the cross-process coordination the per-install scope exists to provide. The registry's own id has the symmetric trap (it once reused the per-install id and every profile became a duplicate row). Depth on the registry side, including why `getMachineIdentity` returns `null` rather than minting: `youcoded-dev/.claude/rules/sync-spaces.md` → Device registry, and `docs/sync-spaces.md` → Device registry.
- **`noteSessionEnded`'s quiescence gate: `session-exit` fires BEFORE the PTY worker dies (CC may still be flushing a final turn), so materialize-on-end MUST skip on timeout.** `noteSessionEnded` (service.ts) releases the materialize guard + runs a TARGETED `materializeOne` that polls the local transcript size until stable across one 750ms probe (max 6s). On TIMEOUT it MUST return without materializing (a `quiesced` flag) — a space→local `renameSync` over a still-open transcript detaches CC's inode on POSIX and loses the flush (a real data-loss bug caught in review). The reconciler/startup sweep catch up a skipped round.
- **`flushSessionToSpace` (holder-takeover local→space) reuses the same wait but pushes REGARDLESS of timeout.** mirrorIn is grow-only and never touches CC's open local file, so that direction is always safe — only the space→local materialize has the inode-detach hazard. The asymmetry is deliberate; don't unify behind one skip-on-timeout rule.
- **Bug-1 browse filter: `sessionIdMap` is a CACHE, not truth — filter its entries to LIVE sessions.** `SESSION_BROWSE` builds its active-set by filtering `sessionIdMap.entries()` to mappings whose desktop session still exists (`sessionManager.getSession(desktopId)`). A stale entry used to hide a CLOSED session from the Resume Browser until restart. Don't revert to raw `sessionIdMap.values()`.
- **Holder-takeover ordering is load-bearing: interrupt(ESC)/quiesce → flush(local→space) → release(lease) → pushMoved → destroySession** (`createHolderTakeover`, takeover.ts). MIRROR-BEFORE-RELEASE: the requester pulls the moment it sees the lease free, so the final turn must already be in the space. RELEASE/push-moved-BEFORE-DESTROY: the enriched `session:moved` push must reach the renderer while the session still exists (so its cwd/claude-id are readable AND the renderer records the moved entry before the destroy arrives). Every step is independently try/caught + an OUTER backstop — the handler is fire-and-forget from a hub event, so a throw = an unhandled rejection. **M2: a native holder branches to `nativeHost.quiesce(desktopId)` instead of the ESC byte** — see "Native provider participation" below for why quiesce is strictly stronger than the interrupt() the Stop button uses.
- **Never-block: any lease query/takeover failure degrades to "proceed with the resume" (+ a warning), never a hard block.** `createRequesterTakeover` runs op:'takeover' → poll `query` every 1s up to 10s (checks free BEFORE the first sleep) → on free: syncNow('personal') → `materializeOne` → acquire; on timeout → the "take over anyway?" force dialog → force-acquire. A lease ERROR at any point lets the resume proceed — never hard-block a user from their OWN conversation. (The device registry that backs the "Your devices" list is keyed per-MACHINE, not by this lease id — `Personal/Devices/<machineId>.json`; see `docs/sync-spaces.md` → Device registry.)
- **Takeover requester's hub-down-with-no-holder outcome is `'undeliverable'`, distinct from `'timeout'`** (migrated 2026-08-12 from the path-scoped rule) — when the hub is down and no holder is reachable, the requester skips the 25s poll and reports `'undeliverable'` instead of waiting out a timeout that cannot succeed. The takeover dialog has three-state copy (`confirm`/`undeliverable`/`force`), pinned verbatim by `takeover-dialog-copy.test.ts`.
- **Hub-down `requester.force` returns `{ok:true}` even when `forceAcquire` was null — a deliberate never-block degradation, NOT a bug to fix into a hard block.** If the hub is unreachable the real holder never got the `takeover-request` either, so both devices can end up live: grow-only mirror churn (visible conflict copies, never silent loss), or a genuine same-file double-writer only on a shared-`~/.claude` dev+built-app machine. The `{ok:true}` is optimistic; surfacing a distinct "hub was down" outcome is an optional refinement, not required.

### MovedGate (the "taken over" surface, App.tsx — renderer, not in these modules but tied to 2b)

- **The "taken over" surface is App.tsx's MovedGate (a full-page gate), NOT a timeline marker — and `destroyedHandler` MUST read `movedSessionsRef.current`, never the `movedSessions` state.** The original marker was appended by `SESSION_MOVED` then wiped back-to-back by the holder's own destroy (`SESSION_REMOVE`), so it never rendered — a taken-over session silently vanished. Fix: the holder KEEPS the pill + still destroys the CC session; clicking it renders `<MovedGate>` (modeled on `TrustGate`: content-area gate at z-10 below chrome, opaque `bg-canvas`, plain words) with **Exit Session** (`session.destroy()` no-ops on the dead session) and **Resume on this device** (runs `handleResumeSession`). No second writer, no un-removable zombie, no competing "session died" banner (the moved branch `return`s before `SESSION_PROCESS_EXITED`/`SESSION_REMOVE`). STALE-CLOSURE TRAP: the handlers are registered once in a `[dispatch]`-dep mount effect, so a `movedSessions` STATE read inside `destroyedHandler` is permanently the initial empty Map — read `movedSessionsRef.current` (`recordMoved`/`clearMoved` keep it in lockstep, updated SYNCHRONOUSLY so the ref is populated before the async post-PTY-death destroy fires). The enriched push carries `claudeSessionId`/`projectSlug`/`projectPath` so Resume needs no second lookup.

## Native provider participation (Plan M2, 2026-07-22 — `conversations/service.ts`, `harness/{native-session-host,session-store}.ts`)

Native (`SessionProvider = 'native'`) sessions now participate in the Conversation Store, transcript mirroring, resume, auto-titling, and takeover the same way CC sessions do, riding the `sessionProvider`-threading and lane-assertion invariants above.

- **Native transcript events feed the store via `noteTranscriptEvent(id, ev, 'native')`.** Records write to `native/<id>.json`; the transcript mirrors into the `native/transcripts/<key>/<id>.jsonl` space lane, read from the native session's LOCAL file at `~/.youcoded/sessions/<nativeStoreSlug(cwd)>/<id>.jsonl`. This is `nativeStoreSlug`, the FROZEN app-private encoding (not `ccProjectSlug`, which additionally uppercases a lowercase Windows drive letter) — a deliberate divergence pinned at `harness/session-store.ts`'s import comment, since unifying the two encodings would orphan every native session file already on disk under the app-private slug.

- **The read side is fully unlocked: `session:get-meta`/`session:browse` are provider-aware on desktop IPC AND the remote WS.** The 2026-07-19 native meta refusal is retired; the renderer-facing sentinel string survives as `META_UNSUPPORTED_FALLBACK` (renamed from `NATIVE_META_UNSUPPORTED`, not deleted — Android still returns it for its own reasons, see `docs/native-runtime.md`). `listPastSessions(activeIds, nativeEntries?)` overlays native store rows onto the CC scan; live-session exclusion (see the materialize-sweep bullet above) still applies to native rows.

- **Resume always offers the model picker for a native session** (the unified `ModelPicker`, pre-filled from the record's `lastUsedModel`) — both from the inline ResumeBrowser AND from the two pre-existing 3-arg native-resume entry points (MovedGate's `onResume`, ProjectView's `onResumeConversation`) via the `pendingNativeResume` modal in App.tsx. The selection becomes `nativeHost.resume(id, cwd, bindingOverride?)`'s binding, applied BEFORE the eager transcript load so the resumed session never briefly renders under the stale stored binding. The session header itself is never rewritten — only the live binding changes.
- **Naming is one policy for both lanes** (`session-namer.ts`, 2026-09-09 — it replaced `native-title-feeder.ts`, whose rule was one bound-model call at the first `turn-complete`, native only). Off / Basic / AI comes from `naming-settings.ts` (`~/.youcoded/config.json` → `naming`); AI reviews at completed replies 1, 3, then every 25, using the chosen naming model or the session's own binding (`providerRegistry.languageModel` + `generateText`, 15s abort, 3 attempts per review, synchronous in-flight guard). A Claude Code session with no separately chosen model is named by the bundled Auto-Title hook instead — its own model, in-session, free — never by silently substituting a paid provider. Writes go through the store + rename fan-out and NEVER touch the session's own JSONL (titles are store-only metadata, matching the "topic files aren't the transcript" pattern CC titling already follows).

## Session name ownership (2026-09-09 — `conversations/naming-{core,store}.ts`, `session-namer.ts`)

- **A name the user typed lives in a SECOND store, not on `ConversationRecord`.** `parseRecord` rebuilds a fixed whitelist (`store-core.ts`), so an older client that reads and rewrites a record drops any field it has never heard of — exactly the mixed-version case ownership has to survive. The sidecar is `Personal/ConversationNames/<provider>/<id>.json`, a directory no older build opens, scans or rewrites. `ConversationRecord.title` stays the compatibility PROJECTION so every existing reader (Resume Browser, chatsearch, remote, peers) shows the right text without knowing the sidecar exists.
<!-- verify: {"path": "youcoded/desktop/src/main/conversations/naming-store.ts", "contains": "ConversationNames|namesRoot"} -->
- **Its merge is per-slot, never activity-ranked.** `manual` and `auto` each carry their own timestamp and join by `laterOf` with the same content tiebreak `mergeRecords` uses, so a rename made on an idle device does not lose to a busier device's newer turn — which is precisely how `title` merges, and precisely why `title` alone cannot carry ownership. A CLEAR is a real event with its own timestamp (`manual: ''`, newer `manualAt`), so "I handed this back on my laptop" beats "I named it yesterday on my phone" instead of losing to it. `replies`/`reviewed` merge by max, so a device that was closed for ten replies cannot rewind the schedule.
- **There is no way back to automatic naming, by design.** Review 3 removed the reset action from the dialog (contract R11), so nothing in the app clears a manual name and no channel exposes one — an unreachable write endpoint on the remote WebSocket is worse than a missing feature. The record still keeps the automatic name a manual one displaced, so a future affordance costs no model call. Filed on `docs/roadmap/chat-data.md`.
- **`noteAutomaticTitle` is the gate; `noteTitleChanged` is the raw writer.** Every generated title must use the first. The live broadcast is gated separately at `applyAutomaticTitle` in `ipc-handlers.ts` — a refused disk write cannot un-paint a session pill — and the namer re-checks ownership again inside the write lock, because the model call is the window in which the user renames.
- **The Auto-Title hook is gated by the app.** `<userData>/naming-mode` (one word, found through the `YOUCODED_NAMING_MODE_FILE` env var every session inherits) and `~/.claude/topics/ask-<id>` are the whole protocol: Off and Basic stop the hook from interrupting a reply to request a title at all, and AI asks only at a scheduled review. That closed the "~6 title requests per conversation / 277 wasted round trips across 46 sessions" waste. A MISSING mode file keeps the old 120s/600s timer, because the same script ships to Android, whose runtime does not schedule reviews yet. WHY the mode lives under userData rather than beside the topic files: `~/.claude/topics` is shared by every YouCoded process on the machine, so a fixed path there let a dev instance set to Off silently switch off auto-titling in the installed app. The ask files are safe to share — they are keyed by the Claude session id.
<!-- verify: {"path": "youcoded/desktop/hook-scripts/title-update.sh", "contains": "naming-mode"} -->
- **Takeover quiesces a native holder instead of sending it the ESC byte.** `NativeSessionHost.quiesce(id)` is STRONGER than the user-facing Stop button's `interrupt()`: it clears the send queue SYNCHRONOUSLY (so no already-queued message can start a new turn after the flush), awaits one macrotask (lets a same-tick `send()` finish its deferred dispatch before aborting), cancels any paused permission ask + aborts the stream, awaits the turn settling, then drains the append chain — postcondition: no further appends happen for the session until a new `send()`. `interrupt()` deliberately does NOT do steps 4–5 (the M1 FIFO queue keeps draining after a Stop-button interrupt); quiescing on takeover and merely interrupting on Stop are NOT interchangeable. `createHolderTakeover` branches to this path when the live holder's provider is `'native'`; the native session lease acquire is re-enabled (gated on `isSyncSpacesEnabled()`, warn-on-denied, mirroring the CC lease path) and `pushMoved` now carries `provider` so the requester's MovedGate/resume flow knows which runtime to resume into.

## Resume Browser & conversation identity (`session-browser.ts`; from the 2026-06-12 missing-sessions investigation)

- **Topic-file mtime IS the conversation-index's `lastActive` source.** `updateConversationIndex()` upserts whenever the topic file's mtime is newer than stored `lastActive`. Anything that (re)writes topic files MUST preserve the original timestamp (`fs.utimesSync`) — `regenerateTopicCache()` is the canonical writer and does. "Now" mtimes create a feedback loop that bumps EVERY session's lastActive each cycle → the 30-day prune never fires + the recent-50 backup pull fetches the wrong sessions (observed: all 627 topic files ≤2 days old).
- **`sessionIdMap` remaps ONLY on `SessionStart`, and ONLY when that SessionStart's `source` is not `startup`.** CC rotates its session id mid-PTY on `/clear` (verified 2026-06-12; `--resume` does NOT rotate, `/compact` rewrites the same file). The SessionStart-only half of the gate stands: subagent/tool hook events carry child session ids and would poison the map. The `source` half was added 2026-07-26 — CC tags each SessionStart `startup | resume | clear | compact`, and only `clear` and an in-session `/resume` are rotations of OUR session. A `startup` arriving for an ALREADY-MAPPED desktop session is a FOREIGN `claude` process announcing itself: `CLAUDE_DESKTOP_SESSION_ID` is inherited by every descendant of the PTY (verified live — a `run-dev.sh` shell carried its parent session's id), so any nested `claude` run reports our desktop id with its own session id. Adopting it repointed the watcher at an unrelated JSONL whose offset-0 replay flooded the chat view with someone else's conversation while the terminal kept showing the real session (observed: a 44MB/15k-line transcript from months earlier). The `source` read is FAIL-OPEN — absent/unrecognized falls back to the pre-fix behavior, never to a chat view stranded on a stale transcript. First sighting is deliberately NOT gated: a resumed conversation's first hook is a `startup` against a non-empty transcript, and refusing it would leave every resumed session's chat empty. Guard: `desktop/tests/session-id-mapping.test.ts`; CC coupling recorded in `docs/cc-dependencies.md`.
<!-- verify: {"path": "youcoded/desktop/src/main/session-id-mapping.ts", "contains": "startup"} -->
- **Resume Browser name precedence: topic file > conversation-index topic > derived-from-first-user-message > "Untitled".** The derived title (`readTranscriptMeta`, mirrored in Kotlin `SessionBrowser`) + content-timestamp ordering exist because (a) the auto-title hook is PostToolUse-gated (chat-only sessions never fire it) + model-compliance-dependent, and (b) sync restores clobber file mtimes so `stat.mtimeMs` lies about recency. Don't simplify ordering back to mtime or drop the head/tail parse. Reads are bounded (256KB head only when untitled / 64KB tail). Android applies the final precedence in `SessionService`'s `session:browse` handler.
- **Literal `Untitled` topic-file content is a placeholder.** Both desktop `readTopic` and Kotlin `SessionBrowser` normalize it (alongside blank + `New Session`) so the index/derived fallback chain applies. Treating the literal string as a real name silently bypasses both fallbacks.
- **Conversation-index keys are CC session UUIDs — `SESSION_UUID_RE` gates the topic scan.** The auto-title flow has the model hand-type `echo "Title" > topics/topic-<id>`; a typo'd id created phantom index entries pointing at no transcript. The scan guard blocks CREATION from malformed ids (existing entries may still be updated — `setSessionFlag` seeds flag-bearing entries before a topic file exists); the prune loop self-heals malformed entries that carry no flags. Flagged malformed entries are KEPT (deleting a user's tag is worse than a dead row).
- **`cleanupPeriodDays` is seeded (365) when absent — never overwritten.** CC's built-in default is 30 days and silently deletes transcripts the Resume Browser lists from. `retention-default.ts` (desktop) + `RetentionDefault.kt` (Android) seed only when the key is missing, respect explicit user values, and never rewrite a corrupt settings.json (it carries hooks + enabledPlugins).

### Slug→path resolution for resume (2026-07-12 two-device dogfood, `session-browser.ts` + `conversations/resolve-local-project.ts`)

A CC slug is the cwd with every separator flattened to `-`, so reversing a slug is AMBIGUOUS when a folder's own name contains a hyphen (`C--Users-desti-youcoded-dev` = `…\desti\youcoded-dev` OR `…\desti\youcoded\dev`). Resume depends on this direction.

- **`walkSlugParts` MUST try the LONGEST leading segment first — do NOT revert to shortest-first.** Shortest-first greedily descends into a stray shorter sibling: with `C:\Users\desti\youcoded` present, the slug resolved to the nonexistent `…\youcoded\dev`, and `session-manager` silently launched `claude --resume` in `$HOME` → every hyphenated-folder session "resumed from the home directory." Pinned by `desktop/tests/slug-path-resolution.test.ts`.
- **Store-backed rows override the slug-walk with the store's exact-basename resolution** (`resolveLocalProject`, shared by the materialize sweep AND the Resume Browser via `buildLocalProjectResolver`), but only when the resolved folder actually holds the transcript. Unambiguous; makes materialize + resume agree on every OS. Cross-OS store-only rows resolve by `projectName` basename too (originalPath is the foreign device's path). Pinned by the cross-OS test in `session-browser.test.ts` + `resolve-local-project.test.ts`.
- **`session-manager.ts`'s `existsSync(cwd) ? cwd : os.homedir()` is a SILENT MASK — it now WARNS on a resume with a missing cwd.** Behavior unchanged; the warning makes a future upstream regression visible instead of a silent wrong-directory resume. Don't remove the warn.
- **ANDROID MIRRORS THE ORIGINAL (PRE-FIX) BUG — all three failure modes still live there (deferred with Android sync, Phase 3).** `SessionBrowser.kt`'s `walkSlugParts` is still SHORTEST-first (its doc comment wrongly claims longest-first); the `session:create` bridge handler DROPS `resumeSessionId` (Android "resume" launches a FRESH session) + passes the raw cwd with no existence check; there is NO `resolveLocalProject`/store overlay; and `listPastSessions` does NOT skip the legacy home-slug symlinks. `SessionRegistry.resumeSession` has the CORRECT cwd derivation but is dead code. When Android resume/sync is picked up, port: longest-first `walkSlugParts`, thread `resumeSessionId` + a cwd existence guard, add a store/basename resolver.
